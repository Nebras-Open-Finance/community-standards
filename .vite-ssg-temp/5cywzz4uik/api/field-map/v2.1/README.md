# Ozone Connect → Standards field map, v2.1

How every data field travels from the LFI's **Ozone Connect** implementation, through the
**API Hub**, to the TPP-facing **Standards** API — and which consent permission exposes it.

Generated by `scripts/build-field-map.mjs` + `scripts/probe-permissions.mjs` in the
`nebras-uat` repository. Do not edit by hand; regenerate and re-export.

```json
  "reviewNeeded": false,

  "permissions": [
    "ReadAccountsBasic",
    "ReadAccountsDetail"
  ],
  "permissionSource": "observed",
  "verified": "live",
  "description": "A unique and immutable identifier produced by the LFI to identify the account resource.This identifier has no meaning to the account owner (User 1).",
  "observedStandardsType": "string",

```

`transform`, `permissionSource` and `verified` are the three status fields; `index.json`
carries the full vocabulary for each under `vocabulary`.

## What the permission data is, and why it is here

The OpenAPI specs declare permissions **per endpoint only** — as bullets in each operation
description. Nothing anywhere states which *field* a permission exposes, so
`ReadAccountsBasic` vs `ReadAccountsDetail` cannot be answered from the specs. Every record
marked `"permissionSource": "observed"` was established by authorising a consent carrying
exactly one permission, fetching the resource, and recording which fields came back. That data
exists nowhere else.

Records marked `"spec-endpoint"` are the endpoint's declared permissions inherited by every
field on it — treat those as *at most* what the field needs, not a measurement.

## Caveats worth surfacing in the UI

- **`verified` is not a quality score.** `spec-only` mostly means "not yet probed", not
  "wrong". Show confidence, do not filter on it silently.
- **Payments (`bank-initiation`) is spec-only.** Live-probing it needs a payment-consent flow
  that the demo TPP does not implement.
- **Some Ozone fields can never be `live`.** `verified` means *seen in the Standards
  response*; a field the Hub drops has nothing to observe on that side.
- **Only one branch of an object-valued `oneOf` can be present at a time**, so sibling
  variants stay unobserved. Array-valued `oneOf`s are fully covered.
- **Pairing is heuristic.** Renames that also change the leaf name (Ozone `id` → Standards
  `AccountId`) are left unpaired with `reviewNeeded: true` rather than guessed at — 149
  records. Do not present those as confirmed mappings.
